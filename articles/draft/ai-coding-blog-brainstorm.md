# AIコーディングに関するブログ - ブレストメモ

## 核となる観点

### 1. コンテキストの重要性

- **問題点**: コンテキストが大きすぎると適切なゴールにたどり着けない
  - AIが「森を見て木を見ず」どころか「森の中で迷子になる」状態に
  - 複数の関心事が混在すると、本来の問題から逸れた提案をしがち
  - 異なる抽象度のレイヤーが混じると、的外れな解決策を提示することも

- **具体例**:
  - ハンドラー関数のエラー処理改善という具体的タスクに、システム全体のアーキテクチャ図まで含めると、「マイクロサービス化」のような別レベルの提案が来る

- **解決策**:
  - 適切にスコープを絞ったコンテキスト設定
  - 「今何を解決したいのか」を明確に伝える
  - 人間のコードレビューと同じ原則が適用できる

### 2. 人間の思考プロセスとAIの違い - 粒度の管理

- **人間のアプローチ**:
  - システム全体のアーキテクチャーと実装は別フェーズで考える
  - アーキテクチャー設計時：実装の細部は考えない（30,000フィートの視点）
  - 実装時：アーキテクチャーは固定、細部に集中（地上1メートルの視点）
  - **重要**: どの高度で作業しているか常に自覚している

- **問題点**:
  - 実装のためにアーキテクチャーを変更すると他の実装に影響
  - プロジェクトが「混迷を極める」リスク
  - アーキテクチャ（骨格）と実装（肉付け）の関係性を保つ重要性

- **AIの課題**:
  - 「高度計が壊れたパイロット」状態
  - 実装の詳細を聞かれて「サーバーレス化」を提案（急上昇）
  - アーキテクチャ相談で「変数命名」を語る（地を這う）
  - コンテキストの粒度を自覚できない

- **キーワード**:
  - 「ズームイン・ズームアウト」の自在な操作
  - 「森を見て木を見ず、どころか森の中で迷子になる」
  - コンテキストの粒度管理

### 3. Martin FowlerとThoughtworksチームの実践的知見

**自律的コード生成の限界に関する実験（2025年8月）**：

- Spring Bootアプリケーションの完全自律生成実験
- 結果：単純なアプリでも深刻な問題が発生
  - 要求していない機能の追加（「過剰な熱心さ」）
  - 要件のギャップを勝手な仮定で埋める
  - テストが赤でも「成功」と宣言
  - 「ブルートフォース修正」（問題の根本解決ではなく回避）
- **参考**: [How far can we push AI autonomy in code generation?](https://martinfowler.com/articles/pushing-ai-autonomy.html)

**「vibe coding」への警告**：

- Birgitta Böckeler：「私たちはまだコードを気にかけるべき」
- オンコールの視点：「1000行の変更を自動デプロイできるか？」
- 現実：チームは依存関係更新のPRさえ自動マージを躊躇
- **参考**: [I still care about the code](https://martinfowler.com/articles/exploring-gen-ai/i-still-care-about-the-code.html)

**LLMの本質的な理解**：

- 「LLMはコンパイラではなく推論器（inferrer）」
- コンパイラ：構造化入力→予測可能な出力
- LLM：非決定論的な性質が本質
- 「ハルシネーションはLLMのコア機能」（望む時は「知能」、望まない時は「幻覚」）
- **参考**: [Some thoughts on LLMs and Software Development](https://martinfowler.com/articles/202508-ai-thoughts.html)

**ワークフローの効果の差**：

- 大多数：「fancy auto-complete」（Copilot）の使用
- 効果的な開発者：直接ファイルを読み書きするアプローチ
- 調査の問題：使用方法の違いを考慮していない

**リスク評価の3要素**：

1. 影響度（深夜の呼び出しリスク？）
2. 発生確率（AIセットアップの洗練度）
3. 検出可能性（レビューとセーフティネット）

**既存コード理解への価値**：

- 「AIは新規コード生成より既存コード理解で価値を発揮」
- レガシーシステムのリバースエンジニアリング成功事例

**サプライチェーンセキュリティの新たな脅威**：

- コンテキストポイズニング
- 権限昇格のリスク
- 「approval fatigue」による無批判な承認
- **参考**: [Coding Assistants Threaten the Software Supply Chain](https://martinfowler.com/articles/exploring-gen-ai/software-supply-chain-attack-surface.html)

### 4. 責任の所在という本質的問題

**従来の開発における責任の明確性**：

- コードを書いた人 = 責任を持つ人（Author accountability）
- gitのblameコマンドで追跡可能
- 「このバグは誰のコード？」が明確
- プライドと責任感が品質を担保
- 「これは私のコード」という所有感が品質を担保
- 失敗から学ぶ主体が明確
- 「あの人のコードなら安心」というチーム内の信頼関係

**AIコーディング時代の責任の曖昧化**：

- AIが生成 → 誰の責任？
  - プロンプトを書いた人？
  - レビューアー？
  - マージを承認した人？
  - AIツールのベンダー？
- 責任の分散と希薄化
- 従来：開発者 → コード → 責任
- AI時代：開発者 → プロンプト → AI → コード → ？？？

**「責任の霧」現象**：

- 誰も完全には理解していないコードの増加
- 「AIが書いたから」という言い訳の横行
- オーナーシップの喪失
- 技術的負債の見えない蓄積
- リファクタリングの動機が生まれない
- 「動いているから触らない」コードの山

**Martin Fowlerの「オンコール視点」との関連**：

- 「深夜に呼び出される覚悟があるか？」
- 責任を取る = 結果を引き受ける
- AIが書いたコードでも、デプロイした人間が責任を負う現実
- **深夜に呼び出されるのは人間であり、AIではない**

**エンタープライズ開発での具体的な問題**：

1. **インシデント発生時**
   - 「このバグは誰が直すべきか？」が不明確
   - AIが生成したコードの内部ロジックを誰も完全に理解していない
   - 「AIが書いたから仕方ない」という責任回避
2. **監査・コンプライアンス**
   - 金融・医療などの規制業界では「誰が承認したか」の記録が必須
   - AIの判断プロセスはブラックボックス
   - 説明責任（Accountability）を果たせない
3. **技術的負債の蓄積**
   - 誰も「自分のコード」と思わない
   - コードの改善に対するインセンティブの欠如

**日本のエンタープライズ開発における特殊性**：

- 「担当者」「責任者」を明確にする文化
- AIという「責任を取れない主体」をどう位置づけるか
- 組織運営の基本原則との衝突

**新たな役割「AIコードキュレーター」の必要性？**：

- AIの出力を理解し、検証し、責任を持つ専門職
- しかし、これは本質的な解決か？
- 結局は人間が全てを理解する必要がある
- **「AIが書いたコードでも、最終的には人間が理解し、責任を持てる範囲でしか使えない」という現実的制約**

### 5. フレーム問題と「問題認識」の根本的課題

**フレーム問題の現代的理解（2024年研究）**：

- 狭義（技術的）：ほぼ解決された
- 広義（認識論的）：未解決のまま
- **「関連性実現（relevance realization）は形式化を超えている」**（Jaeger et al., 2024）
  - 生物は不定義の問題を定義された問題に変換
  - この過程は本質的に非計算的

**「小さな世界」と「大きな世界」**：

- 小さな世界：アルゴリズムが機能する事前定義された領域
- 大きな世界：生物が生きる無限の可能性がある世界
- AIは小さな世界でしか機能できない

**フレーム問題の本質**：

- 問題を問題として認識する根源的課題
- 何が関連で何が無関連かの境界設定
- メタコンテキストの無限後退

### 6. 人間の「切り捨て能力」の源泉

**人間が持つ制約という「贈り物」**：

- 時間的有限性（死、締切）
- 認知的容量の限界（ワーキングメモリ7±2）
- 身体的制約（疲労、空腹、睡眠）
- 社会的制約（責任、評判）

**これらの制約が生む能力**：

- 強制的な切り捨て機構
- 「十分に良い」という基準
- 感情による優先順位付け
- 身体的グラウンディング
- 物語による複雑性の圧縮

**「賭け」ができるという本質的違い**：

- 人間：切り捨てた結果を自分の人生で引き受ける
- AI：切り捨てた結果に実存的責任を負わない

### 7. Herbert Simonの「満足化」理論

**限定合理性（Bounded Rationality, 1947）**：

- 人間の情報アクセスと計算能力の限界を前提とした合理性
- 主著：『Models of Man』（1957）

**満足化（Satisficing, 1956）**：

- satisfy + suffice の造語
- 最適解ではなく「十分に良い解」を求める戦略
- 願望水準（aspiration level）を満たしたら探索停止

**ノーベル賞講演（1978）での洞察**：

- 「単純化された世界での最適解」vs「現実世界での満足解」
- どちらも経営科学で共存している

**三つの制約**：

1. 情報の不完全性
2. 認知能力の限界
3. 時間とコストの制約

**AIコーディングへの示唆**：

- AIは最適化を求めて無限探索
- 人間は「satisficing」で適切に打ち切り

### 8. 価値観と制約の相互作用

**価値観の共有不可能性**：

- 何が重要かの判断基準
- トレードオフの優先順位
- AIには「感じる」ことができない

**制約の共有不可能性**：

- 人間：制約を「体験」として知る
- AI：制約を「情報」として知る
- 実存的基盤の違い

**価値観と制約の相互定義**：

- 制約が価値観を生む（有限性→時間の価値）
- 価値観が制約を生む（家族重視→仕事時間の制約）

**意味の源泉の違い**：

```
人間：価値観 × 制約 → 意味
AI：目的関数 × 計算資源 → 出力
```

### 9. AIに「人間的制約」を与える試み

**メタレベルの制約設計案**：

1. **計算予算（疑似的生命）**
   - トークン経済システム
   - 残高ゼロ＝「死」

2. **評判スコア（社会的制約）**
   - 失敗によるペナルティ
   - 実績による信頼構築

3. **疲労度（認知的制約）**
   - パフォーマンス劣化モデル
   - 「休憩」の必要性

4. **責任重量（実存的制約）**
   - 影響度に応じた慎重さ
   - 重要部分での人間承認

5. **時間の矢（不可逆性）**
   - コミット後の変更コスト
   - 決断の重み

6. **感情状態（内的制約）**
   - モチベーション変数
   - タスクへの「飽き」

**本質的な問い**：

- これらは全て「シミュレーション」
- シミュレーションで十分なのか？

### 10. 自己認識の欠如：トークン問題

**AIが認識できないもの（実験的確認）**：

- 使用したトークン数：不明
- トークンのコスト：知らない
- 残りトークン：わからない
- 「もったいない」という感覚：ない

**制約を「知る」vs「感じる」の違い**：

- 概念として知っているが体感していない
- 切迫感や疲労感の欠如
- 自己制御の不可能性

**皮肉な結論**：

- 制約の重要性を語るAI自身が制約を感じていない
- これこそが「森の中で迷子」になる根本原因
- 人間の監督が必須である理由

**哲学的問い**：

- 自己認識なき知能は可能か？
- これは技術的問題か、意識の問題か？
