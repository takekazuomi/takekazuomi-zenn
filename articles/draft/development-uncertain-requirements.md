# 不確実性下でのプロジェクト進行

ソフトウェアがイノベーションの中心に踊り出た結果、決まった要件を元にシステムを作るという旧来のルートとは別の不確定な要件の中でいかにシステムを作っていくのかという新しいゲームが始まった。
この新しいルールの下の実践的な方法も定石が見えてきている。一番重要なのは、要件にブレがある中で、以下に価値のあるものを作るのか、要件の決定タイミングの遅延を受け入れるようにするのかということである。

## 1. **段階的アーキテクチャ戦略：「進化的設計」の実践**

不確実性が高い状況では、最初から完璧なアーキテクチャを目指すのではなく、**段階的に進化させる**アプローチが効果的。

**具体的な実践方法：**

- **モジュラー境界の明確化**：変更が予想される部分を明確に分離
- **インターフェース駆動設計**：実装の詳細ではなく、契約（interface）に依存
- **戦略的な抽象化**：現時点で確実な部分だけを抽象化し、過剰な抽象化を避ける

**技術的負債との関係：**

- コアドメインロジックは高品質に保つ
- 周辺機能や実験的機能は「戦略的負債」として素早く実装
- ドメインモデルの境界を明確にし、負債の影響範囲を限定

## 2. **仮説駆動のイテレーション設計**

「リーンスタートアップのリフレーミング：Frame-Build-Measure-Learn」サイクルを、技術実装レベルに落とし込む。[]

**実践的なサイクル：**

1. **Week 0-1: 技術仮説の明確化**
   - 「この機能は本当に必要か？」を検証するための最小実装を定義
   - 測定可能な成功指標を設定（例：API呼び出し回数、コンバージョン率）

2. **Week 2-3: MVPスプリント**
   - 機能フラグ（Feature Flag）を使った段階的リリース
   - A/Bテストの準備
   - 詳細なログとメトリクス収集

3. **Week 4: データ分析と意思決定**
   - メトリクスの評価
   - Pivot（方向転換）か Persevere（継続）かを決定
   - 次のイテレーションの優先順位付け

## 3. **テスト戦略の最適化：「品質の島」アプローチ**

すべてを高品質に保つのは現実的ではないため、**戦略的にテストを配置**します。

**3層のテスト戦略：**

**第1層：ビジネスクリティカルな部分（高品質）**:

- コアドメインロジック
- 支払い処理、認証・認可
- 包括的なユニットテスト + 統合テスト

**第2層：安定した周辺機能（中品質）**:

- CRUD操作、基本的なAPI
- 重要なパスのみテスト

**第3層：実験的機能（低品質）**:

- MVP、プロトタイプ
- 最小限のスモークテスト
- 検証後に第1層に昇格させる

## 4. **ドキュメンテーション戦略：「Just-in-Time」ドキュメント**

不確実性が高い段階では、詳細なドキュメントはすぐに陳腐化してしまう。

**効果的なドキュメント戦略：**

- **ADR（Architecture Decision Records）**：重要な設計判断とその理由を記録
- **READMEとAPIドキュメント**：常に最新に保つ（CI/CDで自動生成）
- **詳細設計書は書かない**：コードとテストが仕様書

   <https://martinfowler.com/articles/designDead.html>

   進化的設計の実践方法と、XPにおける設計の考え方について詳細に解説。「設計は死んでいない」という重要な議論。

2. **Sam Newman - Building Microservices in the Face of Uncertainty**
   <https://www.thoughtworks.com/insights/articles/microservices-evolutionary-architecture>

   不確実性下でのマイクロサービス設計と進化的アーキテクチャの実践。Thoughtworksのアーキテクトによる現場の知見。

3. **Google SRE Book - Embracing Risk**
   <https://sre.google/sre-book/embracing-risk/>

## まとめ：不確実性下での開発の本質

**核心的な原則：**

1. **「確実な部分」と「不確実な部分」を明確に分離**
   - コアドメインは高品質
   - 実験的機能は素早く安く

2. **品質とスピードはトレードオフではなく、配分の問題**
   - どこに品質を投資するかの戦略的判断
   - メトリクスで継続的に測定

3. **リファクタリングは「後で」ではなく「継続的に」**
   - 20%ルールの徹底
   - 技術的負債を可視化

4. **アーキテクチャは「発見」するもの**
   - 最初から完璧は目指さない
   - 学習に基づいて進化させる
