## はじめに

マイクロサービスは次のフェーズに来ている。マイクロサービスの「独立デプロイ可能性」という特性は、必ずしも「1つのサービス = 1つのコンテナ（POD）」を意味しない。**コードの独立性**と**デプロイの独立性**は、別々の概念として扱うことができる。それがモジュラーモノリスのアプローチだ。

この記事では、モジュラーモノリスの概念と、マイクロサービスとの違い、実装上の考慮点について解説する。

## コードとデプロイ単位の分離

### 従来の2つのアプローチ

従来、アーキテクチャーの選択肢は主に2つだった：

| アプローチ | コードの構造 | デプロイ単位 | 特徴 |
|-----------|------------|------------|------|
| **モノリス** | 単一の大きなコードベース | 単一のデプロイ単位 | シンプルだが、スケール困難 |
| **マイクロサービス** | 複数の独立したサービス | 各サービスが独立してデプロイ | 柔軟だが、複雑性が高い |

この2つの選択肢では、「コードの構造」と「デプロイ単位」が1対1で対応していた。

### モジュラーモノリスの登場

モジュラーモノリスは、この2つの概念を分離する：

- **開発時**：コードはモジュール単位で独立して開発
- **デプロイ時**：運用要件に応じて柔軟に結合・分離

```text
【従来のアプローチ】
コード構造 ━━ デプロイ単位
   1 : 1 対応（固定）

【モジュラーモノリス】
コード構造（モジュール） ≠ デプロイ単位
   運用要件に応じて柔軟に組み合わせ
```

## モジュラーモノリスの利点

### 1. 開発時の独立性

各モジュールは独立して開発できる：

- **明確な境界**：モジュール間のインターフェースを定義
- **並行開発**：複数チームが独立して開発可能
- **テストの容易さ**：モジュール単位でのテストが可能

### 2. デプロイ時の柔軟性

運用要件に応じて結合・分離を決定できる：

```text
開発環境：
┌─────────────────────────────────┐
│  All-in-One Deployment          │
│  (全モジュールを1つのプロセス)   │
└─────────────────────────────────┘

本番環境：
┌───────────┐  ┌───────────┐  ┌───────────┐
│ Module A  │  │ Module B  │  │ Module C  │
│ + Module D│  │ + Module E│  │ (単独)    │
└───────────┘  └───────────┘  └───────────┘
 (高負荷モジュール)  (関連モジュール)  (独立モジュール)
```

### 3. スケーリングの最適化

必要な部分だけを独立してスケールできる：

- **垂直スケーリング**：特定のモジュールのみリソース増強
- **水平スケーリング**：高負荷モジュールのみ複製
- **コスト最適化**：過剰なリソース確保を回避

### 4. 運用コストの削減

マイクロサービスと比較して：

- **デプロイ単位の削減**：管理すべきサービス数が減少
- **ネットワークオーバーヘッドの削減**：プロセス内呼び出しの活用
- **監視の簡素化**：監視ポイントの削減

## 実装パターン

### パターン1: ビルド時結合

コンパイル時に結合単位を決定：

```go
// main.go（デプロイパターンA：All-in-One）
package main

import (
    "moduleA"
    "moduleB"
    "moduleC"
)

func main() {
    // 全モジュールを起動
    go moduleA.Start()
    go moduleB.Start()
    go moduleC.Start()

    select {} // 待機
}
```

```go
// main.go（デプロイパターンB：Module A単独）
package main

import (
    "moduleA"
)

func main() {
    // Module Aのみ起動
    moduleA.Start()
}
```

### パターン2: 設定ベース結合

起動時の設定で結合単位を決定：

```yaml
# config.yaml（デプロイパターンA）
modules:
  enabled:
    - moduleA
    - moduleB
    - moduleC
```

```yaml
# config.yaml（デプロイパターンB）
modules:
  enabled:
    - moduleA
```

```go
// main.go
func main() {
    config := loadConfig("config.yaml")

    for _, moduleName := range config.Modules.Enabled {
        startModule(moduleName)
    }
}
```

### パターン3: プラグインアーキテクチャ

動的にモジュールをロード：

```go
// プラグインインターフェース
type Module interface {
    Name() string
    Start() error
    Stop() error
}

// ローダー
func loadModules(dir string) []Module {
    // プラグインディレクトリからモジュールをロード
    // Go 1.8以降のpluginパッケージを活用
}
```

## マイクロサービスとの比較

| 観点 | マイクロサービス | モジュラーモノリス |
|-----|-----------------|-------------------|
| **コードの独立性** | 完全に独立 | モジュール単位で独立 |
| **デプロイの独立性** | 完全に独立 | 柔軟（結合・分離可能） |
| **プロセス境界** | サービスごとに独立 | 結合単位に応じて変化 |
| **通信オーバーヘッド** | ネットワーク越し（高） | プロセス内または外（可変） |
| **運用複雑性** | 高（多数のサービス管理） | 中（デプロイ単位が可変） |
| **スケーラビリティ** | サービス単位 | モジュール単位または結合単位 |
| **初期コスト** | 高（分散システムの複雑性） | 中（モジュール分割のみ） |

## 適用シーン

### モジュラーモノリスが適している場合

- **段階的なマイクロサービス移行**：モノリスからの移行パス
- **変動する負荷パターン**：時間帯により負荷が変化する
- **限られたリソース**：運用チームが小規模
- **初期フェーズ**：システムの成熟度が低い

### マイクロサービスが適している場合

- **完全な独立性が必要**：組織横断の複数チーム開発
- **異なる技術スタック**：モジュールごとに最適な技術選択
- **明確な負荷分離**：常に高負荷なサービスが存在
- **高い成熟度**：分散システムの運用経験が豊富

## 実装上の考慮点

### 1. モジュール境界の設計

明確な境界を定義：

```go
// 良い例：インターフェースで境界を定義
package moduleA

type UserService interface {
    GetUser(id string) (*User, error)
    CreateUser(user *User) error
}

// 悪い例：内部実装に直接依存
package moduleB

import "moduleA/internal/database" // NG
```

### 2. 依存関係の管理

循環依存を避ける：

```text
【推奨】
Module A → Module C（共通機能）
Module B → Module C

【避けるべき】
Module A ⇄ Module B（循環依存）
```

### 3. データベースアクセス

結合時にデータベースをどう扱うか：

- **オプションA: Shared Database**（結合時）
  - 同一プロセス内では共有データベース
  - トランザクション管理がシンプル

- **オプションB: Database per Module**（分離時）
  - モジュールごとに独立したデータベース
  - マイクロサービスへの移行が容易

### 4. モジュール間通信

結合単位に応じて通信方式を切り替え：

```go
// 通信アダプター
type ModuleCommunicator interface {
    Call(module, method string, args interface{}) (interface{}, error)
}

// プロセス内通信
type InProcessCommunicator struct {}

// ネットワーク通信
type NetworkCommunicator struct {}

// 結合単位に応じて実装を切り替え
var communicator ModuleCommunicator
if deploymentMode == "monolith" {
    communicator = &InProcessCommunicator{}
} else {
    communicator = &NetworkCommunicator{}
}
```

## まとめ

モジュラーモノリスは、マイクロサービスの「独立性」という概念を、コードレベルとデプロイレベルで分離することで、より柔軟なアーキテクチャを実現する。

### 核心的な利点

1. **開発時の独立性**：モジュール単位で並行開発
2. **デプロイ時の柔軟性**：運用要件に応じて結合・分離
3. **運用コストの最適化**：過度な複雑性を回避
4. **段階的な進化**：モノリスからマイクロサービスへの移行パス

### 適用の指針

- **小規模〜中規模システム**：モジュラーモノリスから開始
- **成長に応じて進化**：必要に応じてマイクロサービスに分離
- **運用成熟度を考慮**：チームの能力に応じた選択

「コードの独立性」と「デプロイの独立性」を別々に考えることで、システムの成長に応じて柔軟にアーキテクチャーを進化させることができる。これがモジュラーモノリスの本質だ。
