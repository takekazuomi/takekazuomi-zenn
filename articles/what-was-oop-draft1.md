# Go言語はオブジェクト指向言語か：言語設計専門家向け詳細分析

Go言語のオブジェクト指向性に関する問いに対し、公式FAQは「**イエスでもありノーでもある**」と回答している。この意図的に曖昧な答えは、Goが伝統的なオブジェクト指向パラダイムを再定義し、継承を排除して合成とインターフェースによる新しいアプローチを採用したことを反映している。本分析では、歴史的文脈、設計者の思想、技術的実装、学術的評価を通じて、Goの独特な位置づけを検証する。

## オブジェクト指向プログラミングの歴史的発展と定義の多様性

### Simulaから始まった階層的オブジェクトモデル

オブジェクト指向プログラミングの起源は、1960年代にOle-Johan DahlとKristen Nygaardがノルウェーコンピューティングセンターで開発した**Simula**にある。Simula 67は、オブジェクト、クラス、継承、仮想手続き、動的オブジェクト生成という基本概念を導入し、両開発者は2001年にACMチューリング賞を受賞した。この時点でオブジェクト指向は**クラスベースの継承階層**として確立された。

1970年代、Alan KayはXerox PARCで**Smalltalk**を開発し、「オブジェクト指向プログラミング」という用語を生み出した。KayのOOP定義は独特で、2003年のメールで以下のように明確化している：「私にとってOOPは、メッセージング、状態プロセスのローカル保持と保護と隠蔽、そしてすべての事柄の極限まで遅延したバインディングのみを意味する」。重要なことに、Kayは**継承をOOPの必須要素とは考えていなかった**。

### 多様化する定義：静的型付けと動的型付けの分岐

1980年代のBjarne Stroustrupによる**C++**は、システムプログラマー向けにSimulaの概念をC言語に導入した。Stroustrupの定義は「抽象化（クラスとオブジェクト）、継承（既存の抽象から新しい抽象を構築）、実行時多態性（実行時バインディング）」の3要素を重視した。1990年代のJavaは、Simulaのオブジェクト指向メカニズムをより忠実に実装し、単一継承とインターフェースのモデルを確立した。

現代の教科書的定義は「**カプセル化、継承、多態性**」の3本柱として標準化されたが、この定義自体が言語設計の選択を制約する規範となっていることをGo設計者は問題視した。

## Go言語設計者の公式見解：継承の意図的排除

### Rob Pikeの「Less is Exponentially More」における設計哲学

Rob Pikeは2012年の講演「Less is Exponentially More」で、Goの設計思想を明確に示した。「**C++とJavaが型階層と型の分類学に関するものだとすれば、Goは合成に関するものだ**」と述べ、さらに「型階層は単なる分類学に過ぎない。重要なのは物事の祖先関係ではなく、それらが何をできるかだ」と型階層の概念自体を批判した。

公式FAQ（https://go.dev/doc/faq）では、「Is Go an object-oriented language?」という問いに対し、以下の回答を提供している：

> 「イエスでもありノーでもある。Goは型とメソッドを持ち、オブジェクト指向スタイルのプログラミングを可能にするが、型階層は存在しない。Goの『インターフェース』概念は、より使いやすく、ある意味でより一般的な異なるアプローチを提供する。」

この回答は、**型階層の不在**と**暗黙的インターフェース満足**がGoの核心的設計決定であることを示している。

### Ken ThompsonとRobert Griesemerの貢献

Ken Thompsonは、UnixとC言語の共同開発者としての経験から、システムプログラミングにおける実用性を重視した。Robert Griesemerは、インタビューで「3人全員が正しいと合意するまで、言語には何も追加されなかった」と述べ、合意形成による慎重な設計プロセスを強調した。

2024年のRob Pikeの振り返り（https://commandcenter.blogspot.com/2024/01/what-we-got-right-what-we-got-wrong.html）では、「Goのインターフェースは設計の初期段階でほぼすぐに生まれた」と述べ、インターフェースベースの設計が当初から中核的要素だったことを確認している。

## Goのオブジェクト指向的特徴の技術的詳細

### メソッドとレシーバー：クラスなきオブジェクト指向

Goは**レシーバー**という概念を通じてメソッドを実装する。値レシーバーとポインタレシーバーの区別により、メモリ管理と変更可能性を明示的に制御する：

```go
type Rectangle struct {
    width, height float64
}

// 値レシーバー（コピーで動作）
func (r Rectangle) Area() float64 {
    return r.width * r.height
}

// ポインタレシーバー（元の値を変更可能）
func (r *Rectangle) Scale(factor float64) {
    r.width *= factor
    r.height *= factor
}
```

メソッドセットの規則により、型`T`のメソッドセットは`T`レシーバーのメソッドのみを含み、`*T`のメソッドセットは`T`と`*T`両方のレシーバーメソッドを含む。この明示的な区別は、暗黙的な`this`や`self`を持つ言語とは対照的である。

### 構造的型付けによる暗黙的インターフェース満足

Goのインターフェースは**構造的型付け**を採用し、明示的な実装宣言を必要としない。型がインターフェースのすべてのメソッドを実装していれば、自動的にそのインターフェースを満足する：

```go
type Stringer interface {
    String() string
}

type Person struct {
    Name string
}

// Person は Stringer を自動的に実装
func (p Person) String() string {
    return p.Name
}
```

この設計により、**消費者定義のインターフェース**が可能となり、既存の型に後からインターフェースを適用できる柔軟性を提供する。

### 埋め込みによる合成：継承の代替メカニズム

Goは継承の代わりに**埋め込み**による合成を提供する。埋め込まれた型のフィールドとメソッドは「昇格」され、埋め込み側の型から直接アクセス可能となる：

```go
type Engine struct {
    Type string
    Horsepower int
}

type Car struct {
    Make string
    Model string
    Engine  // 埋め込み
}

// car.Type、car.Horsepowerとして直接アクセス可能
```

この仕組みは継承に似た効果を提供するが、**ダイヤモンド問題**のような多重継承の複雑性を回避する。

## 他のオブジェクト指向言語との詳細比較

### Java/C#との対比：名目的型付けvs構造的型付け

JavaとC#は**名目的型付け**に基づく古典的OOPを実装し、明示的な`implements`宣言と単一継承を特徴とする。対照的に、Goは構造的型付けにより、型関係の事前宣言なしに自動的なインターフェース満足を実現する。パフォーマンス面では、JavaとC#の仮想メソッド呼び出しはvtableによる動的ディスパッチのオーバーヘッドがあるが、Goは具体型が判明している場合は直接メソッド呼び出しを行う。

### Python/Rubyとの対比：静的ダックタイピング

PythonとRubyの動的ダックタイピングに対し、Goは「**コンパイル時ダックタイピング**」とも呼ばれる静的構造的型付けを提供する。実行時の型エラーを排除しながら、ダックタイピングの柔軟性を維持する。Pythonの多重継承（C3線形化によるMRO）やRubyのミックスインに対し、Goは埋め込みによる合成で同様の効果を達成する。

### C++との対比：複雑性の削減

C++の多重継承、テンプレート、仮想関数、RAII（Resource Acquisition Is Initialization）などの豊富な機能に対し、Goは意図的に機能を制限している。ダイヤモンド問題を合成により回避し、ジェネリクス（Go 1.18以降）はテンプレートより制約され、ガベージコレクションによりデストラクタを不要とする。

### Rustとの対比：トレイトとインターフェース

RustもGoと同様に古典的継承を排除し、トレイトシステムを採用している。主な違いは、Rustのトレイトは明示的実装（`impl Trait for Type`）を必要とするのに対し、Goのインターフェースは暗黙的に満足される点である。両言語とも「**ゼロコスト抽象化**」を目指すが、Rustは所有権システムによるメモリ安全性を、Goはガベージコレクションによる簡潔性を優先する。

## 学術的・理論的観点からの評価

### Featherweight Go：型システムの形式的意味論

2020年のOOPSLAで発表された「**Featherweight Go**」論文（Griesemer、Hu、Kokke他）は、Goの型システムの形式的意味論を提供した。この研究は、Goのサブタイピングが構造的であること、ジェネリクスがモノモーフィゼーションを使用すること、そして「式問題」を構造的インターフェースで解決することを示した。論文URL: https://dl.acm.org/doi/10.1145/3428217

### プログラミング言語理論における位置づけ

学術界はGoを**マルチパラダイム言語**として分類し、手続き型、並行型、構造型、命令型の要素を組み合わせたものと認識している。Rob Pikeの「Go at Google: Language Design in the Service of Software Engineering」（https://go.dev/talks/2012/splash.article）は、Goがコンピュータサイエンス研究ではなく**ソフトウェアエンジニアリング**のために設計されたことを強調している。

### SOLID原則とデザインパターンの実装

研究によると、Goの構造的インターフェースは自然に**インターフェース分離原則**を支援し、合成優先の設計は**依存性逆転原則**と整合する。2010年の「GoHotDraw: Evaluating the Go Programming Language with Design Patterns」（Schmager、Cameron、Noble）は、Goが古典的デザインパターンの実装能力を持つことを実証した。

### 実証的研究による有効性の検証

複数の実証研究が、Goの大規模ソフトウェア開発における有効性を確認している。「Understanding Real-World Concurrency Bugs in Go」（2019、Tu他）は、Go並行性の実践的問題を分析し、「An empirical study of messaging passing concurrency in Go projects」（2019、Dilley、Lange）は、実プロジェクトでのGo並行性パターンを大規模分析した。

## 結論：オブジェクト指向の再定義

Go言語は、オブジェクト指向プログラミングの伝統的定義から意図的に逸脱し、**継承なきオブジェクト指向**という新しいパラダイムを提示している。型階層を排除し、構造的型付けによるインターフェース、埋め込みによる合成、パッケージレベルのカプセル化を採用することで、Goは以下を実現した：

1. **型分類学からの解放**：事前の型関係宣言を不要とし、柔軟な型の組み合わせを可能にした
2. **脆弱な基底クラス問題の回避**：継承階層の変更による連鎖的影響を排除した
3. **明示的な設計意図**：暗黙的な機能ではなく、明示的な合成により設計意図を明確化した
4. **実用的な多態性**：インターフェースによる多態性を、vtableオーバーヘッドなしに実現した

Alan Kayの「メッセージングと遅延バインディング」という原初的OOP概念、Bjarne Stroustrupの「抽象化と多態性」という実装的概念の両方から見ても、Goは部分的にオブジェクト指向的である。しかし、継承を核心とする古典的定義からは明確に逸脱している。

学術的評価は、Goが**ソフトウェアエンジニアリングの実践的要求**を理論的純粋性より優先した成功例として認識している。「Featherweight Go」のような形式的研究は、この実用的アプローチが理論的健全性を保ちながら実現されていることを証明した。Goの設計は、言語設計において「少ないことは指数関数的に多い」というRob Pikeの哲学を体現し、複雑性を削減しながら表現力を維持する新しい道を示している。

# 継承がOOPで重要となった背景とその変遷：C++とJavaコミュニティの視点から

## 1. 継承の誕生と初期の熱狂（1960年代〜1980年代）

### Simulaによる継承の導入（1967年）

継承という概念は、**1967年のSimula 67**においてOle-Johan DahlとKristen Nygaardによって初めて導入された。彼らは当初、シミュレーションシステムにおける階層的な関係を表現するためにこの機能を設計した。Tony Hoareの1966年の「record subclasses」の概念に影響を受け、共通プロパティを持つオブジェクトを**スーパークラス**に集約し、サブクラスが「prefix parts」として親クラスの属性を継承する仕組みを確立した。

興味深いことに、**Alan KayのSmalltalk-72（1972年）には継承が存在しなかった**。Kay自身が1993年に振り返って述べているように：
> 「動的言語でできることは静的にコンパイルされた言語では困難なので、私はSmalltalk-72の機能として継承を意図的に除外し、SmalltalkのLISPのような柔軟性を使ってシミュレートできることを知っていた」

しかし、**Smalltalk-76（1976年）では継承が追加**された。これは「初心者が専門家によって設計されたフレームワーク上に構築できるようにする」という実用的な要求によるものだった。

### C++における多重継承の導入（1980年代）

Bjarne Stroustrupは、1980年代初頭にC++（当初は「C with Classes」）を開発する際、自身のPhD論文でSimulaを使用した経験から**クラスベースの継承を中核機能として採用**した。Stroustrupは1987年の論文で以下のように述べている：

> 「基底クラスの概念は、Cのクラス概念と同様に、エンジニアリングの妥協である」

C++は**1989年のRelease 2.0で多重継承を導入**し、これにより複数の基底クラスから機能を継承できるようになった。Stroustrupは、多重継承が「常に最良の解決策ではないが、時には最良の解決策である」と主張し、表現力の向上を重視した。

## 2. 継承が重要視された理由

### コード再利用の聖杯

1980年代から1990年代初頭にかけて、継承は**「コード再利用の聖杯」**として称賛された。主な利点として以下が挙げられた：

1. **実装の共有**：共通機能を基底クラスに集約し、派生クラスで再利用
2. **階層的モデリング**：現実世界の「is-a」関係を自然に表現
3. **多態性の実現**：仮想関数テーブル（vtable）による動的ディスパッチ
4. **増分的開発**：既存クラスを拡張して新機能を追加

### 型システムとの統合

C++やJavaにおいて、継承は**型システムと密接に結びついていた**。サブクラスは自動的にスーパークラスのサブタイプとなり、これによりLiskov置換原則に基づく多態的な使用が可能となった。

## 3. 問題の顕在化（1990年代）

### 脆弱な基底クラス問題（Fragile Base Class Problem）

1990年代後半になると、継承の根本的な問題が広く認識されるようになった。**1998年のMikhajlovとSekerinskiの論文**「A Study of the Fragile Base Class Problem」は、この問題を体系的に分析した：

> 「この問題は、コード継承を実装再利用メカニズムとして採用するオープンなオブジェクト指向システムで発生する。システムのユーザーが開発した拡張を知らないシステム開発者は、一見受け入れ可能な基底クラスの改訂を行うが、それが拡張を破壊する可能性がある」

### 継承がカプセル化を破壊する

**Alan Snyderの1986年の論文**「Encapsulation and Inheritance in Object-Oriented Programming Languages」で既に指摘されていた問題が、1990年代に広く認識された：

- サブクラスは親クラスの実装詳細に依存する
- 親クラスの内部変更がサブクラスを破壊する
- 「open recursion」（thisへの動的ディスパッチ）が予期しない相互作用を引き起こす

## 4. デザインパターン運動と「合成優先」の台頭（1994年〜）

### Gang of Fourの提言（1994年）

**1994年の「Design Patterns」**（Gamma、Helm、Johnson、Vlissides著）は、継承の問題に対する決定的な転換点となった。彼らは明確に述べている：

> 「継承がカプセル化を破壊すると言われることがよくある」

そして、有名な原則を提示した：
> **「Favor object composition over class inheritance」（クラス継承よりオブジェクト合成を優先せよ）**

彼らは、DecoratorパターンやStrategyパターンなど、継承の代わりに合成を使用する具体的なパターンを提示した。

### C++コミュニティの反応

C++コミュニティでは、多重継承の複雑さが認識され始めた：

- **ダイヤモンド問題**の処理の困難さ
- 仮想継承の複雑性
- 大規模システムでの保守性の低下

Stroustrup自身も後年、継承の過度な使用について警告するようになり、**「Design and Evolution of C++」（1994年）**で、継承階層の設計は「APIを設計するように」慎重に行うべきだと述べた。

## 5. JavaとEffective Javaの影響（2001年〜）

### Joshua Blochの「Effective Java」（2001年初版、2008年第2版）

Joshua Blochの**「Effective Java」のItem 16（第2版ではItem 18）「Favor composition over inheritance」**は、Javaコミュニティに決定的な影響を与えた：

> 「継承は強力なコード再利用の方法だが、常に最適なツールではない。不適切に使用すると、脆弱なソフトウェアにつながる」

Blochは具体例として、`HashSet`を拡張した`InstrumentedHashSet`クラスで、`add`と`addAll`メソッドの相互呼び出しによる予期しない動作を示した。

### Javaコミュニティでの実践

JavaのAPIデザインにおいて、以下の変化が見られた：

1. **finalクラスの増加**：`String`、`Integer`などの基本クラスを継承不可に
2. **インターフェースの重視**：実装継承より型継承を優先
3. **合成とデリゲーション**：Decoratorパターンの広範な採用（`BufferedReader`など）

Blochの提言：
> 「継承のために設計し文書化するか、さもなければ継承を禁止せよ」

## 6. 現代における継承の位置づけ（2010年代〜現在）

### 言語レベルでの対応

現代のプログラミング言語は、継承の問題に対して様々な対応を行っている：

**制限的アプローチ：**
- **Java/C#**：`final`/`sealed`キーワードで継承を明示的に禁止
- **Kotlin**：クラスとメソッドはデフォルトで`final`（継承には`open`が必要）
- **Go**：継承を完全に排除し、埋め込みと合成のみ提供

**代替メカニズム：**
- **Rust**：トレイトシステム（継承なし、合成とトレイト実装）
- **TypeScript/JavaScript**：ミックスインとプロトタイプチェーン
- **Swift**：プロトコル指向プログラミング

### 現代のベストプラクティス

2020年代のOOPコミュニティでは、以下が広く受け入れられている：

1. **「is-a」関係の厳密な適用**：真の型階層のみに継承を使用
2. **浅い継承階層**：2-3レベルまでに制限
3. **Template Methodパターン**：継承を使う場合の推奨パターン
4. **インターフェース分離**：小さく特化したインターフェース
5. **依存性注入**：合成を容易にするフレームワークの活用

## 結論：継承から合成へのパラダイムシフト

継承は1960年代後半から1990年代まで、OOPの**「キラー機能」**として称賛されたが、大規模システムでの経験を通じて、その限界と危険性が明らかになった。

**脆弱な基底クラス問題**は、継承の根本的な欠陥を露呈した：継承はカプセル化を破壊し、変更に対して脆弱なシステムを生み出す。この認識は、1994年のGang of Fourから始まり、2001年のEffective Javaで決定的となった**「合成優先」**のパラダイムシフトをもたらした。

現代では、継承は**「必要悪」**として扱われ、真に必要な場合にのみ、慎重な設計と文書化のもとで使用されるべきツールと認識されている。新しい言語設計では、継承を完全に排除するか、厳密に制限する傾向が顕著である。

この変遷は、ソフトウェアエンジニアリングが**理論的理想から実践的経験**へと成熟した過程を象徴している。継承という「エレガントな」概念が、現実世界の複雑性と保守性の要求に直面し、より実用的な合成アプローチに道を譲ったのである。

# Goがtypeとclassを分けない理由：設計者による議論と思想

## 1. 設計の出発点：「Less is Exponentially More」

Rob Pikeは2012年6月のGo SF meetingでの講演「**Less is exponentially more**」で、Goの型システムの核心的な設計思想を明らかにした。この講演は、Goがなぜclassを持たず、統一的なtype概念を採用したかを理解する上で最も重要な文献である。

### 型階層への根本的な批判

Pikeは講演で以下のように述べている：

> 「型階層は単なる分類学（taxonomy）だ。すべての型の親を決め、AがBを継承するか、BがAを継承するかを決めなければならない。ソート可能な配列は、ソートする配列か、配列として表現されたソーターか？型がすべての設計問題に対処すると信じるなら、その決定をしなければならない。私はそれがプログラミングについて考える馬鹿げた方法だと信じている。**重要なのは物事の間の祖先関係ではなく、それらがあなたのために何ができるかだ**」

この発言は、クラスベースの設計が持つ根本的な問題を指摘している：現実世界の分類学をコードに持ち込むことの無意味さである。

## 2. 統一的な型システムの利点

### あらゆる型にメソッドを定義可能

Goの革新的な決定の一つは、**「methods for any type (no classes)」**である。Rob Pikeは以下のように説明している（InformIT, 2011）：

> 「Goはオブジェクト指向だが、クラスの概念を持たない。型システムはより一般的だ。**あらゆる型—整数や文字列のような基本型でさえ—メソッドを持つことができる**。これにより、継承や他のオブジェクト指向技術を、クラスだけよりも広範に適用できる」

```go
// 基本型にメソッドを定義
type MyInt int

func (m MyInt) IsPositive() bool {
    return m > 0
}

// 使用例
var num MyInt = 42
fmt.Println(num.IsPositive()) // true
```

この設計により、JavaやC++のような「プリミティブ型」と「オブジェクト型」の人為的な区別が排除された。

### 直交的な機能設計

2007年9月21日、Rob Pike、Ken Thompson、Robert Griesemerがホワイトボードに書いた初期の設計目標には、**「直交的（orthogonal）な機能」**という概念があった。Pikeは以下のように述べている：

> 「Goの機能は直交的であることを意図している。それらが組み合わされたとき、明確で予測可能な方法で相互作用する」

この直交性により、以下が実現された：

1. **型定義とメソッド定義の分離**
   ```go
   // 型定義
   type Rectangle struct {
       Width, Height float64
   }
   
   // メソッドは別の場所で定義可能
   func (r Rectangle) Area() float64 {
       return r.Width * r.Height
   }
   ```

2. **インターフェースと実装の分離**
   - 明示的な「implements」宣言不要
   - 構造的型付けによる自動的なインターフェース満足

## 3. クラスを排除した理由

### 型駆動プログラミングへの反対

Rob Pikeは2020年のEvrone インタビューで明確に述べている：

> 「**私は型駆動プログラミング、型階層、クラスと継承のファンではない**。多くの非常に成功したプロジェクトがそのように構築されてきたが、このアプローチは重要な決定を設計段階の早い時期に、経験がそれに影響を与える前に押し付けると感じている」

### 合成による問題解決

「Less is exponentially more」でPikeは以下のように述べている：

> 「**C++とJavaが型階層と型の分類学に関するものなら、Goは合成に関するものだ**」

Doug McIlroyの1964年の言葉を引用しながら、Pikeは続ける：

> 「プログラムを庭のホースのように結合する方法があるべきだ—データを別の方法で処理する必要があるときに、別のセグメントをねじ込む。これがGoの方法でもある」

## 4. 統一的type概念がもたらす簡潔性

### 削除された複雑性

「Less is exponentially more」でPikeが挙げた、GoがC/C++から削除した機能リスト（抜粋）：

- **no classes** - クラスなし
- **no subtype inheritance (no subclasses)** - サブタイプ継承なし
- **methods for any type** - あらゆる型にメソッド定義可能
- **no "this" in methods** - メソッドに「this」なし
- **methods are just functions** - メソッドは単なる関数
- **interfaces are just methods (no data)** - インターフェースは単なるメソッド（データなし）

### 型システムの一般化

GoのFAQ（go.dev/doc/faq）では以下のように説明されている：

> 「メソッドはGoではC++やJavaよりも一般的だ：それらは、プレーンで『アンボックスされた』整数のような組み込み型を含む、**あらゆる種類のデータに対して定義できる**。それらは構造体（クラス）に制限されない」

## 5. 設計者間の合意形成

### 満場一致の原則

Robert Griesemerは、言語機能の追加について以下のように述べている：

> 「3人全員（Pike、Thompson、Griesemer）が正しいと合意するまで、言語には何も追加されなかった」

この厳格な合意形成プロセスにより、クラスという複雑な概念は最初から排除された。

### Cからの出発、C++の拒否

初期のメールスレッドでRobert Griesemerは述べている：

> 「出発点：C、明らかな欠陥を修正し、不要なものを削除し、いくつかの欠けている機能を追加する」

注目すべきは、**出発点がC++ではなくC**だったことである。Pikeは以下のように説明している：

> 「Robertが出発点はCであってC++ではないと言ったことに注目してほしい。特にKenがいたからこそ、彼はC本来を意味していたと思う」

## 6. 型の一般性がもたらす表現力

### printfの例

Pikeは、Goの型システムの一般性を示す例として、fmt パッケージを挙げている：

> 「Goのフォーマット済み印刷ライブラリ、パッケージfmtは、インターフェースとメソッドを使用して、基本型から任意のユーザー定義オブジェクトまで、あらゆる値を完全な型安全性でprintfのようなAPIで印刷する方法を提供する」

これは、統一的な型システムがあるからこそ可能となる。

## 7. 結論：簡潔性による表現力の向上

Rob Pikeは「Less is exponentially more」を以下の言葉で締めくくっている：

> 「それでも、その長い簡素化と欠けている部分のリストにもかかわらず、GoはCやC++よりも表現力があると私は信じている。**Less can be more**（少ないことは多いことだ）」

Goがtypeとclassを分けない理由は、以下に集約される：

1. **分類学的階層の拒否**：現実世界の分類をコードに持ち込むことの無意味さ
2. **直交的な設計**：型定義とメソッド定義を分離し、柔軟な組み合わせを可能に
3. **一般性の追求**：すべての型を同等に扱い、人為的な区別を排除
4. **合成優先**：継承による「is-a」関係より、合成による「can-do」関係を重視
5. **簡潔性による表現力**：複雑な機能を削除することで、より強力な表現を実現

この設計決定は、Ken Thompson（Cの共同開発者）、Robert Griesemer（V8 JavaScriptエンジンの開発者）、Rob Pike（Plan 9の設計者）という、異なる背景を持つ3人の設計者が満場一致で合意した結果である。彼らは、数十年のシステムプログラミング経験から、**型階層の複雑さが問題を解決するよりも多くの問題を生み出す**ことを理解していた。

Goの成功は、この「Less is exponentially more」の哲学が正しかったことを証明している。クラスという概念を排除し、統一的なtype概念を採用することで、Goはより簡潔で、より表現力があり、より保守しやすい言語となった。
