## マイクロサービスにおけるアーキテクチャーパターンの適用

最近やってるプロジェクトでは、マイクロサービスアーキテクチャー[^arch1]を採用している。このプロジェクトでは、アーキテクチャの統一、複数チームでの並行開発、開発スピードを重視している。各サービス間のインターフェイスは固く、実装の縛りは少なく、チームに自由度を持たせつつも、カオスにならないようにコントロールしようという方針だ。[^memo1]

アーキテクトとして、サービス分割からAPI設計、実装まで見てきて、その中で気が付いたことを整理しておく。その中でも重要なのは、「袋小路に向かってひたすら進んでる」と感じるケースで、その１つが、Hexagonal ArchitectureやClean Architectureを各サービス内部に律儀に適用してるケースだ。他にも、ユニットテストを過剰にロンドン派[^ut]寄りにしてしまうケースもあるが、これは今回は触れない。

これはなかなか典型的な**over-engineering**だ。「Enterprise Hello World」[^ehw]のような過剰設計で、まあ、見ていて「これはちょっと...」と思ってしまう。マイクロサービスという分割で既にシンプルになっているはずが、内部を複雑化している。なぜそう言えるのか、順を追って説明する。

## マイクロサービスとは何か

マイクロサービスについては、Martin FowlerとJames Lewisが良い定義を出している。それは、**単一のアプリケーションを小さなサービス群の組み合わせとして構築する手法**[^arch2]だ。個々のサービスは自身のプロセス上で動作し、HTTPのリソースAPIなど軽量の機構により通信を行う。

Sam Newmanは、これをもっと簡潔に「小さく、自律的で、協調して動作するサービス」と表現している[^arch19]。なかなか分かりやすい。ここで重要なのは、2つの核心的な特性だ：

- **独立したデプロイ可能性**：他のサービスに影響を与えずに個別にデプロイできる
- **情報隠蔽**：各サービスがその実装の詳細を隠す

また、AWS、Azure、Google Cloudなど主要なクラウドプロバイダーは、マイクロサービスの運用上の特性として、**拡張性**と**回復性**を強調している[^arch20]。

ここには、「分けることによって複雑性を軽減したい」という大きなモチベーションがある。ただ、話はそう単純ではない。分けることでサービス内部の複雑性は減るが、サービス間の統合や連携における複雑性が増加する。つまり、**複雑性の移動**が発生する。複雑性は消えてなくなるのではなく、別の場所に移動する。

- **サービス内部**：単純化される（各サービスは小さくシンプル）
- **サービス間**：複雑化する（分散システムの課題：ネットワーク、一貫性、監視、デバッグ）

この複雑性の移動を理解するには、まず「分ける」ということの本質を考える必要がある。

> [!Note]
>
> ここでは、話を単純化するために、一般的に言われる「マイクロサービス」の定義を書いているが、実プロジェクトでは、マイクロサービスとモジュラーモノリスを混ぜたような構成にしている。分けるという観点ではマイクロサービス。デプロイ、プロセス分離という観点では、モジュラーモノリスの部分採用した構成だ。「余白はそれを書くには狭すぎる」ので、何時か別途書いてみようと思う。

## 分けるということ - Separation of Concerns

Separation of Concerns（関心の分離）は、ソフトウェア開発の基本原則[^soc]。分割することで複雑さをコントロールする。

これを提唱したDijkstra [^ewd]は、本質を突いてうまく表現している:

> Let me try to explain to you, what to my taste is characteristic for all intelligent thinking. It is, that one is willing to study in depth an aspect of one's subject matter in isolation for the sake of its own consistency

要するに、問題を分割して、各側面に個別に集中できるようにすることが、複雑性に対処する基本だということだ。

Dijkstra は続けて、その理由を端的に述べている：「we have very, very small heads」（我々の頭は、とてもとても小さい）。人間の脳は、複数の関心事を同時に深く考えることができない。分離は、**人間の認知能力という物理的制約に対する対処法**だ。

言い換えると、人間には同時に扱えるコンテキストに限界がある。認知負荷を減らし、一度に考えるべきことを減らす。分けることで取り扱いやすくなる。これは、普遍的な原則としても通用するがソフトウェア開発では特に重要だ。

### ソフトウェアにおけるマトリョーシカ構造

ソフトウェア開発では、複雑性が爆発的に増加する。この複雑性をコントロールするために、分割を繰り返し適応していく。その構造は、マトリョーシカのようで、分割されたものを見るとさらに分割されたものが出てくる。

```text
ブロック → 関数 → パッケージ → gRPCサーバー → マイクロサービス → インターネットサービス
```

分割することで、コンテキストが限定され、粒度も細かくなり、深く考えられるようになる。

考えてみれば、このマトリョーシカ構造の各段階で、我々は異なる「関心事」に集中してる。関数を書くときは、その関数の責務だけを考える。マイクロサービスを設計するときは、そのビジネス機能だけを考える。各レベルで考えるべきことが違う。

つまり、**Separation of Concerns をどのようにコントロールするか = 適切なレベルで適切に分割すること**だ。

## 複雑性の移動とトレードオフ

ここで重要な原則を理解する必要がある。それは、**分割したものは、いずれ統合して動かす必要がある** ということだ。

分割は万能薬ではなく、内在するコストが付随する：

- **統合のコスト**：分割されたコンポーネント間の通信、協調、整合性の維持
- **管理のコスト**：複数のコンポーネントの監視、デプロイ、バージョン管理
- **理解のコスト**：システム全体の動作を理解するために複数の場所を見る必要がある

**分割にはトレードオフがあり**、複雑性は消えるのではなく、形を変えて別の場所に移動する。この「複雑性の移動」をどうコントロールするかが、アーキテクチャー設計の本質の１つでもある。

では、システムを分割する方法にはどのようなアプローチがあるのだろうか？ある程度の規模になったシステムを分割する方法には、なかなか対照的な2つのアプローチがある[^arch3]。

### 水平分割（Horizontal Decomposition）

1990年代から主流となっていた層化アーキテクチャは、2000年代にHexagonal Architecture、2010年代にClean Architectureという形で進化した。このアプローチでは、以下のような特徴がある：

- Hexagonal Architecture / Clean Architectureが採用[^arch4][^arch5]
- 1つのアプリケーション内部を技術的関心事で層（レイヤー）に分割
- ビジネスロジックを他の層（UI、DB、外部API）から切り離す
- 目的：ビジネスロジックの独立性と再利用性の確保

つまり、アプリケーション内部で横方向に技術層を分離することで、ビジネスロジックを守ろうとする設計だ。この考え方自体は悪くない。ビジネスロジックが最も重要なパーツで、それ以外は変わってもビジネスロジックは変わらないという前提がある。

### 垂直分解（Vertical Decomposition）

対照的に、マイクロサービスアーキテクチャでは異なるアプローチをとる：

- システム全体をビジネス機能単位で複数のサービスに分割
- 各サービスは単純で見通しの良いコードで実装
- **サービス境界そのものが最も強力な分離メカニズム**として機能する[^arch6]
- 目的：サービス間の独立性と複雑性の分散化

こちらは、システム全体を縦方向にビジネス機能で分割することで、複雑性を分散させる設計だ。

```text
【水平分解 - Hexagonal/Clean Architecture】
┌─────────────────────────────────────┐
│  Application                        │
│  ┌────────────────────────────────┐│
│  │ ═══════════════════════════  ││ ← 水平方向に技術層で分離
│  │ Presentation Layer             ││
│  │ ───────────────────────────  ││
│  │ Business Logic Layer           ││
│  │ ───────────────────────────  ││
│  │ Data Access Layer              ││
│  └────────────────────────────────┘│
└─────────────────────────────────────┘
      複雑性がアプリケーション内部に集中

【垂直分解 - マイクロサービス】
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│ User Service │    │ Order Service│    │ Product Svc  │
│              │    │              │    │              │
│  handler     │    │  handler     │    │  handler     │
│  service     │    │  service     │    │  service     │
│  repository  │    │  repository  │    │  repository  │
│  (Simple)    │    │  (Simple)    │    │  (Simple)    │
└──────────────┘    └──────────────┘    └──────────────┘
      ↑                   ↑                   ↑
  ビジネス機能で     ビジネス機能で      ビジネス機能で
  垂直方向に分離     垂直方向に分離      垂直方向に分離

      複雑性がサービス間に分散
```

### 分離の強さが複雑性の扱いを変える

水平分解と垂直分解、両方とも「分ける」アプローチだが、**分離の強さが根本的に違う**。

水平分解は、プロセス内のレイヤー分離だ。同じメモリ空間内で、インターフェースと依存性注入で分離する。複雑性は、この層間の調整に集中する。

垂直分解は、プロセス境界を越えた分離だ。ネットワーク越しのAPI通信になる。各サービス内部はシンプルになるが、サービス間の統合に複雑性が移動する。

この**分離の強さの違いが、複雑性の移動先を決める**。

:::details コラム：強い分離を水平分割に適用した失敗例

初期のエンタープライズJavaBean（EJB）は、この原則に反して失敗した典型的な例だ。アプリケーション内部のレイヤー間通信に、リモートインターフェースを使った強い分離を適用した[^ejb-oracle]。

EJBの問題は、Martin Fowlerが「分散オブジェクトの第一の法則」で警告した通りだった：**プロセス内呼び出しとリモート呼び出しの区別は、カプセル化できない**。プロセス内呼び出しは高速で信頼性が高いが、リモート呼び出しは桁違いに遅く失敗の可能性がある[^fowler-dist-ms]。

結果として：

- レイヤー呼び出しごとにマーシャリング、ネットワーク転送、アンマーシャリングが発生
- 引数のコピー（pass-by-value semantics）のコスト
- 著しいオーバーヘッドによる性能劣化

**水平分割には軽い分離、垂直分割には強い分離**が適している。分離の強さと分割の方向を間違えると、複雑性が爆発する。
:::

**Sam Newman（『Building Microservices』著者）**[^arch7]：「マイクロサービスにおいて、サービス境界を越えた通信はすべてネットワーク越しのAPI呼び出しである。これは、プロセス内のレイヤー分離よりも遥かに強力な分離メカニズムだ」

## 本題：Hexagonal/Clean はマイクロサービスに不要

マイクロサービスで分けることによって、シンプルにするのが目的だ。だから、従来のモノリシックな巨大アプリケーションを作る場合の技法（Hexagonal/Clean Architecture）を、わざわざ小さなサービスに持ち込むのは本末転倒。これは個人的にも違和感がある。**ここが本題だ。**

### Hexagonal/Clean が解決していた問題はマイクロサービスの外側に移動する

Hexagonal/Clean Architectureは、単一の大きなアプリケーション内部で、ビジネスロジックを技術的な詳細から守るために生まれた。しかし、マイクロサービスでは、この問題の性質が変わる。

**サービス境界がすでに強力な分離を提供してる**からだ。ビジネスロジックの独立性は、サービス単位で達成される。データベースの詳細も、外部APIとの連携も、すべてマイクロサービスの外側（サービス境界を越えた領域）の問題になる。

### 2つの分解アプローチを同時適用すると複雑性が増幅する

マイクロサービスアーキテクチャ（垂直分解）を採用してる環境で、各サービス内部にHexagonal ArchitectureやClean Architecture（水平分解）を適用すると、**2つの分解アプローチが競合**する[^arch3]。

具体的には以下のような問題が発生する：

- **分離の重複**：サービス境界と内部レイヤーで二重の分離が発生
- **複雑性の増幅**：複雑性が掛け算的に増加（サービス数 × レイヤー数）
- **開発速度の低下**：マイクロサービスの利点（独立デプロイ、迅速な変更）が損なわれる

マイクロサービスは、**小さく、単純であることが価値**だ[^arch8]。各サービス内にHexagonal Architectureのような複雑なレイヤー構造を導入すると、以下のような問題が発生する：

- **コードの複雑性が増加**：インターフェース、アダプター、ポートといった抽象レイヤーが追加される
- **開発速度の低下**：単純な変更でも複数のレイヤーを跨ぐ必要がある
- **認知負荷の増大**：開発者が理解すべき構造が増える

結果として、マイクロサービスの利点である「小さく理解しやすい」という特性が失われてしまう。これじゃ本末転倒で、「何のためにマイクロサービスにしたの？」ということになる。

```text
【パターン1：垂直分解のみ（推奨 ✅）】

┌─────────┐    ┌─────────┐    ┌─────────┐
│Service A│    │Service B│    │Service C│
│シンプル  │    │シンプル  │    │シンプル  │
└─────────┘    └─────────┘    └─────────┘
     ↕              ↕              ↕
  ──────────────────────────────────────
        サービス間の統合（3箇所）

  複雑性のポイント = 3箇所


【パターン2：垂直 + 水平（非推奨 ❌）】

┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│ Service A   │  │ Service B   │  │ Service C   │
│             │  │             │  │             │
│ ┌─────────┐ │  │ ┌─────────┐ │  │ ┌─────────┐ │
│ │ Handler │ │  │ │ Handler │ │  │ │ Handler │ │
│ └────┬────┘ │  │ └────┬────┘ │  │ └────┬────┘ │
│      ↓      │  │      ↓      │  │      ↓      │
│ ┌─────────┐ │  │ ┌─────────┐ │  │ ┌─────────┐ │
│ │ Service │ │  │ │ Service │ │  │ │ Service │ │
│ └────┬────┘ │  │ └────┬────┘ │  │ └────┬────┘ │
│      ↓      │  │      ↓      │  │      ↓      │
│ ┌─────────┐ │  │ ┌─────────┐ │  │ ┌─────────┐ │
│ │Repository│ │  │ │Repository│ │  │ │Repository│ │
│ └─────────┘ │  │ └─────────┘ │  │ └─────────┘ │
└─────────────┘  └─────────────┘  └─────────────┘
       ↕                ↕                ↕
  ────────────────────────────────────────────────
          サービス間の統合（3箇所）

  複雑性のポイント = サービス間（3箇所）
                   + 各サービス内の層（6箇所 × 3）
                   = 21箇所（7倍に増加！）
```

**Martin Fowler**[^arch9]：「マイクロサービスの利点の1つは、各サービスが独立して理解・変更可能なことだ。サービス内部を過度に複雑にすると、この利点が損なわれる」

## 全体感とスケールの問題

ここで、もう少し大きな視点から考えてみよう。

### クライアント-サーバーという大きな分割

最近のサービスのほとんどは、**2つの大きなコンポーネント**で構成されている：

1. **クライアントアプリ**：スマホ、タブレット、ブラウザなどのインターネット端末上で動作
2. **サーバーサービス**：バックエンドで動作するビジネスロジックとデータ管理

この2つを単純化して見ると、実は**プレゼンテーションレイヤーとビジネスロジックレイヤー**のようなものだ。ここにも分割がある。

### マトリョーシカの入れ子構造

さらに重要なのは、それぞれのコンポーネントの中に、さらに分割された構造があるということだ：

```text
インターネットサービス全体
├── クライアントアプリ（Presentation Layer）
│   ├── UI Components
│   ├── State Management
│   └── API Client
│
└── サーバーサービス（Business Logic + Data Layer）
    ├── マイクロサービス A
    │   ├── handler
    │   ├── service
    │   └── repository
    ├── マイクロサービス B
    └── マイクロサービス C
```

ユーザーが利用する**インターネットサービス全体**という観点で見ると、Clean Architectureのような同心円状の構造として理解することもできるだろう。

### スケールに応じた適切な設計

しかし、ここで重要な原則がある：**分解した先にさらに無用なレイヤー構造を持ち込むことは、無用な複雑性を生むことになる**。

これは、**全体感の問題**だ。

"Hello World"を出力するだけのプログラムに、DIコンテナを駆使して、複数のレイヤーを用意して、インターフェースを定義して...という設計をする意味はない。それは「Enterprise Hello World」のような過剰設計だ。

同様に、すでにマイクロサービスとして分割されている小さなサービスの内部に、さらにHexagonal ArchitectureやClean Architectureの複雑なレイヤー構造を持ち込むのは、スケールに対して不適切だ。

**適切な粒度で適切な分割を行う**。これがアーキテクチャー設計の要諦だ。

## マイクロサービスに適した構造

マイクロサービス内部では、**シンプルな2層構造**で十分だ：

```go
// マイクロサービス内部の推奨構造（2層）
user-service/
├── cmd/
│   └── server/
│       └── main.go           // エントリーポイント
├── internal/
│   ├── handler/              // gRPC/HTTPハンドラー（境界）
│   │   └── user_handler.go
│   └── model/                // ビジネスロジック + データアクセス
│       └── user.go           // Transaction Scriptパターン
└── proto/
    └── user/v1/
        └── user_service.proto

// ❌ 過度に複雑な構造（Hexagonal/Clean適用）
user-service/
├── cmd/
├── internal/
│   ├── domain/              // ドメインモデル（Pure）
│   ├── ports/               // インターフェース定義
│   │   ├── inbound/         // ユースケース
│   │   └── outbound/        // リポジトリ
│   ├── adapters/
│   │   ├── primary/         // HTTPハンドラー
│   │   └── secondary/       // DB実装
│   └── application/         // アプリケーションサービス
└── ... (さらに増える)
```

**推奨される原則**[^arch10]

マイクロサービス内部では、以下のシンプルな2層構造で十分だ。逆に、これで足りないようなら、「マイクロ」とは呼べない可能性があるので注意した方が良い：

- **ハンドラー層**：gRPC/HTTPのリクエストを受け取り、モデル層を呼び出す（API境界）
- **モデル層**：トランザクションスクリプトパターン[^transaction-script]でビジネスロジックとデータアクセスを統合

この構造は、見通しが良く、保守しやすく、変更に強い。

**重要な考え方**：

- **リポジトリ層の入れ替えを考慮する必要はない**：各サービスは特定の永続化実装（PostgreSQL、MongoDB等）の機能を最大限に生かす実装にする
- **余計なレイヤーは不要**：クラウドでは、リソースの一滴は血の一滴。無駄な抽象化はコストとパフォーマンスの両面で損失
- **API互換性と内部実装の分離**：サービスはAPIレベルでの互換性維持を保証し、内部実装は秘匿する。内部実装は自由に変更できる
- **ミニマリストな実装**：必要最小限のコードで、変更に耐える実装を目指す

### データベース技術の選択は実装の詳細

マイクロサービスでは、**各サービスが独自のデータベース技術を選択できる**ことが利点だ[^arch12]。例えば以下のように、サービスごとに最適なデータベースを選択できる：

- User Service → PostgreSQL
- Order Service → MongoDB
- Analytics Service → Cassandra

この選択は、**サービス外部には公開されない実装の詳細**だ。サービス境界がすでに強力な分離を提供してるため、サービス内部でさらにデータベースを抽象化する必要はない。

**Chris Richardson（『Microservices Patterns』著者）**[^arch13]：「Database per Service パターンにおいて、データベースはサービスのプライベートな実装の詳細である。他のサービスは、APIを通じてのみアクセスすべきだ」

:::details コラム：アーキテクチャー設計の哲学
### 複雑性を操作するということ

アーキテクチャーを操るということは、**複雑性を操作すること**に似ている。

複雑性自体を完全に消すことはできない。できるのは：

- **扱いやすいサイズにする**：大きな問題を小さな問題に分割
- **ポイントを移動する**：複雑性が発生する場所を、扱いやすい場所に移す
- **適切に分散する**：一箇所に集中させず、複数の場所に分散

### 発見としてのアーキテクチャー

決して、どこにでも適応できる「究極のアーキテクチャー」的なものがあるわけではない。アーキテクチャーとは、**発見していくもの**のように思う[^arch18]。

江戸時代の仏師・円空は、もともと木の中に居る仏を掘り出して仏像を作ったという。木材に仏像の形を押し付けるのではなく、木が持っている自然な形を活かしながら、そこに潜んでいる仏の姿を見出していく。

アーキテクチャーも同じではないだろうか。システムの本質、ビジネスの要求、技術的制約、チームの特性...これらが持っている自然な形を見出しながら、**元々あるものをアーキテクチャーという形にしていく**。

### 良いアーキテクチャーとは

短く言うと、**「自然とこうなる」とか「当たりまえにこうなる」**という感じが良いアーキテクチャーな気がする。

無理に形を押し付けるのではなく、システムの本質に沿った自然な形。過度に複雑にするのでもなく、過度に単純化するのでもなく、ちょうど良い粒度での分割。

### 分離と全体の相補性

「分けることで全体が見えなくなる」という懸念があるかもしれない。しかし、Dijkstraが示したように「我々の頭は、とてもとても小さい」。**全体を同時に理解することは、そもそも不可能**だ。

重要なのは、**各抽象化レベルで「全体」が存在する**ということだ：

- 関数のレベルでは、その関数が「全体」
- マイクロサービスのレベルでは、そのサービスが「全体」
- インターネットサービスのレベルでは、クライアント-サーバー全体が「全体」

各レベルで適切な粒度の分割を行う。**レベルを跨いだ過度な分割は逆効果**だ。

適切な分割なしに全体を理解することは不可能。David Parnasが示したように、適切な分割基準（変更の隠蔽）により、モジュール単位での理解が全体理解につながる[^arch15]。Larry Constantineが定義した高凝集度・低結合度は、独立性の高いモジュールの組み合わせとして全体を理解できることを意味する[^arch16]。

そして、Fred Brooksが警告したように、複雑性は消えるのではなく移動するだけだ[^arch17]。マイクロサービスは、モノリス内部の複雑性をサービス境界に移動させた。さらに各サービス内部を複雑化すれば、複雑性が「二重に」存在することになる。

**適切な粒度で適切に分割する**。これがアーキテクチャー設計の要諦であり、マイクロサービスにおいては「サービス境界で分割し、各サービス内部はシンプルに保つ」という形になる。
:::

## 最後に

マイクロサービスを採用するなら、各サービス内部はシンプルに保つのが筋だと思う。

### この記事の核心

マイクロサービス（垂直分解）とHexagonal/Clean Architecture（水平分解）は、**両立しない分解アプローチ**だ。

- **垂直分解**：ビジネス機能でシステムを複数のサービスに分割。サービス境界が強力な分離メカニズムとして機能
- **水平分解**：技術的関心事でアプリケーション内部を層に分割。ビジネスロジックを守る
- **同時適用の問題**：複雑性が掛け算的に増加。マイクロサービスの「小さく理解しやすい」という利点が失われる

**分解のアプローチは1つに絞る**。これが複雑性をコントロールする鍵だ。

### マイクロサービス構築の実践原則

具体的には、以下を意識すると良い：

1. **サービス境界を最優先に**：垂直分解（ビジネス機能での分割）で複雑性を分散
2. **サービス内部はシンプルに**：見通しの良い3層構造（handler → service → repository）で十分
3. **余計な抽象化を避ける**：Hexagonal/Cleanのような複雑なレイヤー構造は不要
4. **リポジトリの抽象化**：複数の実装を切り替えるためであり、テスト目的ではない

これだけでも、なかなか保守しやすいシステムになる。

### どちらを選ぶべきか

構築するシステムの性質によって選択が変わる：

| システムの種類 | 推奨アプローチ | 理由 |
|---------------|---------------|------|
| モノリシックアプリケーション | 水平分解（Hexagonal/Clean） | アプリケーション内部の複雑性管理に有効 |
| マイクロサービス | 垂直分解のみ | サービス境界が分離を提供、内部はシンプルに |
| 小規模システム | モノリス推奨 | マイクロサービスは複雑性のコストが高い[^arch8] |

**注意**：小規模なシステムでマイクロサービスを採用するのは、かえって複雑性が増すので要注意だ。Martin Fowlerも言ってるように[^arch8]、単純なシステムならモノリスで十分。
